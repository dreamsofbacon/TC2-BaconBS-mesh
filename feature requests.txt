
# Feature Requests and Verification Status

Last reviewed: 2026-09-20. `main` is on v0.1.690. bbs.local is on v0.1.683, deployed 2026-09-20 14:58 UTC and healthy; BaconBBS-VT2 and Chattanooga take the same signed instruction over MQTT and have not been re-checked since. ## Open: User Experience and Defects

- [ ] The SSH front end can stop authenticating anyone while systemd still reports it active. Seen 2026-09-20: every login refused for hours, cleared by a restart, no exception and no log line. Now instrumented (v0.1.687) but not explained -- the next occurrence should name itself. Watch for it.
- [ ] Remaining small snags from the field report, none of them blocking: the connect banner says "[0] goes back, and disconnects from the main menu" while the tip three lines below says "[0] always goes back"; "Send !R"/"Send !AU" phrasing is mesh-DM wording on a terminal where you type; "9" in Linked Devices redisplays with no error where every other menu says "Invalid choice."; the Hardware stats list shows bare numeric model keys (133, 254) beside real names; success messages end in a table-flip emoji; the Services screen is the only top-level menu with no Tip line.
- [ ] Trivia King saves a score for a game in which nothing was answered ("Final score: 0 (0 questions). Your score was saved.").
- [ ] Ask Nomad answers arrive asynchronously on whatever screen you have moved to, with nothing identifying which question they answer, and a follow-up carries no context from the previous one.
- [ ] Seven accounts on bbs.local have a blank alias. An account with no alias cannot be addressed or displayed; find the creation path that can produce one before cleaning them up.

- [ ] Ask Nomad answers are longer than the radio budget. The live system prompt asks for replies under 170 characters and `gemma4:e4b` ignores it, so answers are truncated at `max_response_bytes` (1600 on bbs.local) on the way out. A prompt problem rather than a code one, but the truncation is what a radio user actually sees.

- [ ] Names follow the account (v0.1.661). Mail "From" shows the sending device's current account alias. Public Chatter from a linked radio shows the device name, then the account in brackets (radio feed and web page). New bulletins and channel comments record the writing device and show its account alias; the device travels to peers in a `POSTAUTHOR` frame, only to nodes advertising `auth`. - [ ] Single-node sync status (deployed in v0.1.674). With no peers in `[sync] bbs_nodes` the nav pill read "no peer reports" and the settings page said "Unknown", which looks like a fault on a node that simply has nobody to compare against. Both now say so: "single node" in the pill, "Single node: no sync peers configured" on the page. Covered by tests; only matters on a node run alone, which none of the three currently are.
- [ ] Account moves and unlinks now travel between nodes (deployed in v0.1.674). A link carries the time it was made and the newer one wins, so a move made on one node is true on the others instead of leaving them delivering that person's mail to the radio they moved away from. An unlink leaves a tombstone and a new `ACCTUNLINK` frame, gated on the new `acctmv` capability, so a peer holding the old link cannot put it back; tombstones are dropped after 60 days. An `ssh:` login is still never moved or unlinked remotely -- it is its own account and the password lives with it. Covered by tests. Needs a real two-node test: move a device on one node, confirm the other follows and mail routes to the new account; then unlink and confirm it does not come back.
- [ ] Nomad's BBS vocabulary (deployed in v0.1.674). `[gateway] ai_system_prompt` is empty on bbs.local, so nothing had ever told the model what things are called here. An operator's own prompt still replaces it entirely. Covered by tests; needs a live question to Nomad once a model is installed there.
- [ ] Fleet status traffic. Before: about 13 `FLEETVER`, 13 `NODEVER` and 13 `FLEETSTATUS` a minute in steady state. v0.1.674 rate-limited the advert that rides the apply check and brought it to 4 a minute each, measured 2026-09-18 -- all of it inbound, because three other call sites on the scheduled sync tick still advertised unconditionally. - [ ] SD card write load (deployed in v0.1.674). Connection events -- which every log line becomes -- are now held in memory and written in batches of 50 or every 5 seconds, in one transaction, instead of a connection, an fsynced commit and a whole-table prune per line; the prune runs once per 500 rows, so the table can overshoot its cap by a few hundred. The log alone drops to synchronous=NORMAL and can lose its last few seconds in a power cut; mail, bulletins and comments keep synchronous=FULL and are never buffered. Covered by tests. Measure the real write rate on bbs.local and forgecam after deploying, since the 25 GB/day figure was measured before this. Back up `config.ini` from both nodes.

- [x] News feeds are fleet-wide and owned by the node that added them (v0.1.680). The feed list is rows in `fleet_feeds`, advertised as `FEED|` on the periodic tick and gated on a new `feed` capability. A feed carries the node that created it, and only that node may edit or retire it; every other node gets a block instead, which is local and never leaves that node. Newest stamp wins, so a node offline through an edit cannot undo it; a retirement leaves a tombstone, because without one the next peer to sync hands the feed back. Change-driven, so a settled list costs no airtime, and a frame too big for a LoRa packet is skipped and named in the log rather than truncated into something the far end drops. Managed from Settings > API Gateway: add, edit, retire, hide, re-check, with a feed fetched and read once on save and the first headline returned as proof. The News menu grows a third level only once feeds are filed into more than one category; doors filed nowhere land under Other, which exists because without it an unfiled door is unreachable -- that is how the built-in Hacker News door vanished the first time a second feed was added. Driven through the real web-admin routes, 26 checks, 2026-09-20.
