## Needs Verification: User and Service Workflows

- [ ] Single-node sync status (on `main`, not yet deployed). With no peers in `[sync] bbs_nodes` the nav pill read "no peer reports" and the settings page said "Unknown", which looks like a fault on a node that simply has nobody to compare against. Both now say so: "single node" in the pill, "Single node: no sync peers configured" on the page. Covered by tests; only matters on a node run alone, which none of the three currently are.
- [ ] Account moves and unlinks now travel between nodes (on `main`, not yet deployed). A link carries the time it was made and the newer one wins, so a move made on one node is true on the others instead of leaving them delivering that person's mail to the radio they moved away from. An unlink leaves a tombstone and a new `ACCTUNLINK` frame, gated on the new `acctmv` capability, so a peer holding the old link cannot put it back; tombstones are dropped after 60 days. An `ssh:` login is still never moved or unlinked remotely -- it is its own account and the password lives with it. Covered by tests. Needs a real two-node test: move a device on one node, confirm the other follows and mail routes to the new account; then unlink and confirm it does not come back.
- [ ] Nomad's BBS vocabulary (on `main`, not yet deployed). `[gateway] ai_system_prompt` is empty on bbs.local, so nothing had ever told the model what things are called here. The BBS now sends its own prompt when that setting is blank: short replies, and Bulletins / Channels / Mail / Public Chatter by name, never "forums" or "threads". An operator's own prompt still replaces it entirely. Covered by tests; needs a live question to Nomad once a model is installed there.
- [ ] Fleet status traffic (on `main`, not yet deployed). It was not rollout noise: measured on bbs.local 2026-09-17, steady state was about 13 `FLEETVER`, 13 `NODEVER` and 13 `FLEETSTATUS` frames a minute, because the apply check ran every 60 seconds and advertised to every peer each time regardless of change. The periodic advert now goes out only when something changed -- target, version, rollout state -- or every 15 minutes; the apply check itself still runs every minute, and a deploy still advertises immediately. Covered by tests. After deploying, recount the frames and confirm a deploy still reaches all three nodes promptly.
- [ ] SD card write load (on `main`, not yet deployed). Connection events -- which every log line becomes -- are now held in memory and written in batches of 50 or every 5 seconds, in one transaction, instead of a connection, an fsynced commit and a whole-table prune per line; the prune runs once per 500 rows, so the table can overshoot its cap by a few hundred. The log alone drops to synchronous=NORMAL and can lose its last few seconds in a power cut; mail, bulletins and comments keep synchronous=FULL and are never buffered. Covered by tests. Measure the real write rate on bbs.local and forgecam after deploying, since the 25 GB/day figure was measured before this. Back up `config.ini` from both nodes.
- [ ] Open-list fixes, on `main` and not yet deployed. Quick Commands print each command's fields (`!SM,,to,,subject,,message`). Deleting the message you are reading asks "Delete ...? [Y]es [0]No" first, in both mail readers -- it used to take effect on the keypress, in both, so the note that `!CM` already confirmed was wrong. A linking code that is not six digits says so instead of sharing the "Invalid or already-used code" reply. A lone `0` at the channel comment composer means Back, as it does elsewhere, rather than becoming the comment's last line. `!AU` returns to the screen it was typed on. Covered by tests; not yet used on a radio.
- [ ] Public Chatter layout is under test again. `tests/test_chatter_colours.py` and `tests/test_chatter_filters.py` now read `templates/radios.html`, the page that is actually served, and the orphaned `templates/public_chatter.html` is deleted. Three things the served page had lost came back with it: the light-theme colour palette (station colours were dark-theme only), the legend's focus ring, and the plain styling for the "not recorded" chip. Checked in tests against the template, not in a browser.
- [ ] SSH terminal output (v0.1.661): text wraps at word boundaries to the client's terminal width and follows window resizes; menu titles, options, tips and errors are coloured whenever the client opens a terminal. Covered by tests; not yet seen in a real SSH client.
- [ ] SSH password reset from a linked radio (v0.1.661): Settings & Profile > Linked devices > `[7] Reset SSH password` sends a one-time six-digit code, valid 10 minutes; the user logs in as `reset:<alias>` with it (or types that at the shared gate's username prompt) and sets a new password. Codes are stored hashed; guessing is limited to 5 tries an hour per address and per account. Covered by end-to-end SSH tests, and the reset table exists on bbs.local; not yet tried from a real radio.
- [ ] Names follow the account (v0.1.661). Mail "From" shows the sending device's current account alias. Public Chatter from a linked radio shows the device name, then the account in brackets (radio feed and web page). New bulletins and channel comments record the writing device and show its account alias; the device travels to peers in a `POSTAUTHOR` frame, only to nodes advertising `auth`. Posts made before this keep their stored name. Covered by tests; bbs.local has the new author columns and all its peers advertise `auth`, but no post with a recorded author has been seen crossing the fleet yet.
- [ ] Delete several mail messages at once. Web admin (v0.1.663): the Mail page has a checkbox on each row, select-all, and "Delete selected" with a confirmation; the old per-row Delete sat in the last column, usually scrolled off screen. Radio and SSH (v0.1.664): Mail > Read and `!CM` take `D`, then numbers such as `3,5`, `3-7` or `ALL` (Mail > Read uses the message numbers it prints, `!CM` its list positions), show what will be deleted, and delete on `Y`. Both use the same delete as a single message, so peers drop their copies. Covered by tests; not yet used on the fleet.
- [ ] SSH connections shown as "Unknown" in Mail: v0.1.652 fixed the Relay Directory, and a walk through the other Mail screens on a copy of the live database found no other "Unknown" label. Confirm from a real SSH session.
- [ ] Multi-device accounts: successfully link a second device, set/observe a shared alias, unlink with confirmation, protect the final device, and test rate/expiry limits.
- [ ] Moving a device between accounts (v0.1.652): a code entered on a device already on another account names both accounts and offers to move it (`[Y/N]`), using the code only on Yes; the same account is called "your account"; SSH logins are never moved. This fixes a dead end, since turning on relay or requesting a code gives a device its own account and a device alone on its account could never be unlinked. Deployed and covered by tests; not yet tried on a real device.
- [ ] Relay mail to MQTT users (v0.1.652): restored after v0.1.650 treated only Meshtastic and MeshCore nodes as relay targets. Covered by tests; no MQTT user has had relay mail queued on the live fleet.
- [ ] SSH account lifecycle: registration, repeated login/session limits, password reset/change flows, and account linking across client identities.
- [ ] Gateway: live allow-listed HTTP GET, store-and-forward, rate limiting, and a peer-gateway Nomad follow-up. Ask Nomad itself fails until a model is installed (see Open: Product and Operations).
- [ ] Relayed mail on air (v0.1.650). MeshCore: mail goes one chunk at a time, each only after the recipient's radio acknowledges the last; unanswered attempts retry at 10 min, 30 min, 1 h, 3 h, then every 6 h. Meshtastic: sent when the recipient was recently heard; delivered if every packet is acknowledged, otherwise sent once more the next time they are heard. Both stop after 7 days, and the mail stays in the mailbox. None of this has been exercised on air. Live so far: 28 undeliverable `ssh:` deliveries were cancelled on bbs.local, and Materva's pending MeshCore mail is left to Chattanooga, whose radio has his contact.
- [ ] Cross-node relayed mail: confirm the node that can reach a recipient delivers, and the `MAILDLV` receipt stops a second node sending a duplicate DM.
- [ ] Full welcome on first contact (v0.1.644) and `!WELCOME`/`!HELLO` (v0.1.649): deployed and covered by end-to-end emulator tests, not yet confirmed from a real radio.
- [ ] Chattanooga's delete markers catch up. After v0.1.643 it held 26 to bbs.local's 31; the five missing are for test channels it never had. Markers are only compared when content differs, so this should settle at the next content repair.
