# Feature Requests and Verification Status

Last reviewed: 2026-09-14. `main` is at v0.1.655; the fleet (bbs.local, BaconBBS-VT2, Chattanooga) runs v0.1.651. v0.1.652-v0.1.655 are merged with CI green but not deployed. Status is based on repository history, focused regression coverage, the live `baconbot` SSH beta-test sessions, field-validation notes, and checks against the running code and live `bbs.local` database. Detailed UX findings are in `BBS-BETA-TEST-REPORT-2026-09-07.md`.

The Pico cache node is now its own project, `dreamsofbacon/baconbbs-pico`, with its own feature request file.

## Merged, Awaiting Deploy (v0.1.652-v0.1.655)

- [ ] Relay Directory: the browse footer said `[#] Write`, which read as a key to press, and `#` did nothing. It now shows the numbers to type (`[1-4] Write`), and `#` or `W` explains what to type. SSH logins and emulator sessions in the directory are labelled "SSH" and "Emulator" instead of "(Unknown)". (v0.1.652)
- [ ] Project Nomad errors: the gateway reported a 404 as a wrong API path. The real cause is that the Nomad instance at `ai.bmcse.com` has no AI models installed, and Nomad passes Ollama's "model not found" through as a 404. On a 404 the gateway now asks the server which models it has and names the missing one. The server still needs a model installed (see Open: Product and Operations). (v0.1.652)
- [ ] Node View names the node you are on: "This node (burlington)". Checked against a copy of the live bbs.local database. (v0.1.652)
- [ ] Web chatter names the radio that heard each message, e.g. "Heard by 🥓 BBS (burlington)" or "Heard by MeshCore radio (chattanooga)", instead of the radio's key. Remote radios are named by network and by their `[node_names]` entry; a remote radio's own name is never known locally. Checked against a copy of the live bbs.local database. (v0.1.652)
- [ ] Linking a device that is already linked: the same account is now called "your account"; a different account is named on both sides with an offer to move the device (`[Y/N]`), and the code is used only on Yes. This fixes a dead end: turning on relay or requesting a code gives a device its own account, and a device alone on its account could never be unlinked. SSH logins are never moved. (v0.1.652)
- [ ] Relay mail to MQTT users restored. v0.1.650 treated only Meshtastic and MeshCore nodes as relay targets and would have cancelled mail for MQTT users; none were queued on the live fleet. (v0.1.652)
- [ ] A plain `pytest` from the repo root runs the same suite as CI (`pytest.ini`: `testpaths = tests`). It had been collecting `test_remote_db.py`, a one-off script, and crashing before any test ran. (v0.1.653)
- [ ] Removed 58 files that were not part of the BBS: 27 game-bot scripts and the Trivia King answer key (`trivia_answers.pkl`), 14 debug and inspection scripts, Visual Studio's `.vs/` and project files, two empty databases, and a duplicate root `trivia.db`. `.gitignore` now keeps editor state and those stray databases out. (v0.1.654)
- [ ] Moved `pico_node/`, `hardware/` and the six Pico tests, with their history, to `dreamsofbacon/baconbbs-pico` (private). The BBS keeps subscriber mode (`[sync] subscriber_nodes`). (v0.1.655)

## Open: Product and Operations

- [ ] Install an AI model on the Project Nomad server. `https://ai.bmcse.com/api/ollama/installed-models` returns an empty list, so every Ask Nomad question fails; the BBS asks for `qwen2.5:3b` (`[gateway] ai_model` on bbs.local). Install that model in Nomad's AI Assistant, or set `ai_model` to one that is installed.
- [ ] Reduce SD card write load. Both nodes write roughly 25 GB/day (bbs.local: 8 GB SanDisk from 2019; forgecam: 16 GB SanDisk from 2015, 166 GB in one week). The cause is diagnostic logging: every connection event and sync frame is its own fsynced commit, and `_prune_connection_events` rewrites the table after every single insert. Estimated consumer-card life at this rate is months, not years. Back up `config.ini` from both nodes in the meantime.
- [ ] Investigate fleet status traffic. In the 10 minutes after the v0.1.643 deploy, bbs.local logged about 140 each of `FLEETVER`, `NODEVER` and `FLEETSTATUS` frames. Not rechecked since; it may only have been rollout announcements.
- [ ] Account moves and unlinks apply only on the node where they are made. By design a peer never lets a sync frame move a device between accounts (`apply_synced_account_link`), so other nodes keep the old link and route that device's mail by it.
- [ ] Investigate the single-node status icon behavior.
- [ ] Consider combining Linux services where that improves deployment and failure isolation.
- [ ] Restructure modules where it reduces complexity without disrupting the running system.
- [ ] Extend MeshCore support with user account rooms and relayed room text.
- [ ] Repoint `tests/test_chatter_colours.py` and `tests/test_chatter_filters.py` at `templates/radios.html`. ## Needs Verification: User and Service Workflows

- [ ] Multi-device accounts: successfully link a second device, set/observe a shared alias, unlink with confirmation, protect the final device, test rate/expiry limits, and (after v0.1.652) move a device between two accounts with a code.
- [ ] SSH account lifecycle: registration, repeated login/session limits, password reset/change flows, and account linking across client identities.
- [ ] Gateway: live allow-listed HTTP GET, store-and-forward, rate limiting, and a peer-gateway Nomad follow-up. Ask Nomad itself fails until a model is installed (see Open: Product and Operations).
- [ ] Relayed mail on air (v0.1.650). MeshCore: mail goes one chunk at a time, each only after the recipient's radio acknowledges the last; unanswered attempts retry at 10 min, 30 min, 1 h, 3 h, then every 6 h. Meshtastic: sent when the recipient was recently heard; delivered if every packet is acknowledged, otherwise sent once more the next time they are heard. Both stop after 7 days, and the mail stays in the mailbox. None of this has been exercised on air. Live so far: 28 undeliverable `ssh:` deliveries were cancelled on bbs.local, and Materva's pending MeshCore mail is left to Chattanooga, whose radio has his contact.
- [ ] Cross-node relayed mail: confirm the node that can reach a recipient delivers, and the `MAILDLV` receipt stops a second node sending a duplicate DM.
- [ ] Full welcome on first contact (v0.1.644) and `!WELCOME`/`!HELLO` (v0.1.649): deployed and covered by end-to-end emulator tests, not yet confirmed from a real radio.
- [ ] Chattanooga's delete markers catch up. After v0.1.643 it held 26 to bbs.local's 31; the five missing are for test channels it never had. Markers are only compared when content differs, so this should settle at the next content repair.
- [ ] Radio administration on real hardware: the `/radios` send, rename, remove-contact and refresh operations have only ever run against test fakes.

- [x] Channel Directory: browse, create, read-back, threaded comments, and comment read-back.
- [x] User Profiles: short name, bio, activity stats, and linked-device menu, now shown at the top of Settings & Profile.

- [x] MeshCore interface: companion serial/TCP/BLE configuration, contact inventory, encrypted direct-message mapping, broadcast-channel mapping, receive event conversion, and automatic 160-byte frame enforcement/chunking.

- [x] Dual-radio bridge software behavior: independent per-radio sync links share the local database, enforce each transport's frame limit, and isolate a failed radio link from the other interface.
